# Mejora 27 - Google Calendar

## Funcionamiento

Calendar usa un token OAuth temporal en memoria con el scope `calendar.app.created`, separado de Google Drive. La usuaria debe pulsar **Conectar**; tras recargar o expirar la autorización debe hacerlo de nuevo. No se guarda el token en `localStorage`. Con este permiso no se llama a `calendarList.list`: la primera conexión crea un calendario privado y verifica su ID, nombre y marcador mediante `calendars.get`. En otro dispositivo debe introducirse el ID mostrado por el primero para vincular el mismo calendario; también se verifica antes de usarlo. Un fallo de red ambiguo al crear deja el alta bloqueada para revisión, en vez de crear copias sucesivas. Cerrar o bloquear la ventana de Google permite reintentar; una autorización sin respuesta caduca a los 45 segundos.

Los gastos pendientes con fecha válida se representan como eventos individuales con ID determinista por movimiento. Se listan todas las páginas antes de reconciliar. La creación se verifica por lectura, y una respuesta perdida se resuelve buscando el mismo ID. Si `events.insert` devuelve HTTP 409, se lee el ID exacto: un evento activo solo se acepta si su estado, contenido, marcador privado y movimiento coinciden; un evento `cancelled` se restaura con `PATCH`, el ETag vigente e `If-Match`. Una segunda lectura debe encontrarlo `confirmed` y completamente coincidente antes de contabilizarlo como creado. Si falta el ETag, llega HTTP 412 o falla la verificación, la intención de alta se conserva y se informa conflicto. La ficha del movimiento se abre por enlace aunque haya filtros activos; si no existe localmente, se ofrece abrir el panel de Drive. El enlace no cambia datos financieros.

La interfaz habilita ediciones y eliminaciones condicionales. Solo se intentan si existe una transición local observada, el evento remoto aún coincide con la base anterior y trae ETag. `PATCH` y `DELETE` envían `If-Match`; HTTP 412 deja el evento remoto intacto, conserva la operación local pendiente y señala un conflicto. No se reintenta la misma escritura a ciegas. La lectura posterior verifica las escrituras aceptadas; para `DELETE` acepta tanto HTTP 404 como un evento con estado `cancelled`.

El diario `mis-finanzas-calendar-v1` guarda solo autorización deseada, ID del calendario, recordatorios y cambios de Calendar pendientes. No modifica `mis-finanzas-offline-v1` ni la base remota de Drive. Los recordatorios aceptan hasta cinco valores únicos entre 0 y 40320 minutos. Se sincronizan automáticamente los cambios locales mientras el token sea válido; si no hay internet o autorización, quedan pendientes y se reintentan al reconectar o pulsar **Sincronizar ahora**.

Una alta pendiente conserva su ID de creación aunque se edite antes del primer envío; el evento se crea con los datos actuales. Al confirmar una edición o eliminación se reconoce solo la versión enviada: un pago posterior permanece pendiente para la siguiente pasada. Las escrituras del diario entre pestañas se concilian por campo e ID, preservando el ID del calendario y las operaciones independientes; cambios incompatibles sobre el mismo ID quedan marcados para revisión. La importación JSON y el reemplazo desde Drive se distinguen de las ediciones locales. Sus operaciones previas se marcan para revisión y nunca se convierten automáticamente en una orden de borrar un evento.

## Regla conservadora multidispositivo

- Un evento no se elimina porque su movimiento falte en la copia local. Para borrar por pago o eliminación lógica se requiere una transición local observada y guardada, un evento remoto igual al anterior y su ETag. Una ocurrencia futura distinta conserva su evento.
- Si Drive trae un movimiento ya pagado pero Calendar aún conserva el evento y este dispositivo no observó la transición, se muestra conflicto. No se elimina el evento ni se informa una sincronización completa.
- Una edición se aplica solo si el evento sigue coincidiendo con la versión local anterior. Una respuesta distinta o un ETag cambiado deja el caso pendiente.
- En un calendario ya existente, un pendiente antiguo sin historial local de alta o reversión no genera automáticamente un evento ausente: podría haber sido pagado en otro dispositivo. El caso se informa como conflicto. Las altas locales observadas y las reversiones sí se pueden crear con ID determinista.
- La primera activación en un calendario recién creado incorpora los pendientes locales. Si otra copia estaba desactualizada, esa incorporación inicial puede requerir revisión humana. No se fusionan movimientos ni se decide qué dispositivo tiene razón.

## Límites y riesgos pendientes

El ensayo manual reportado confirma la restauración real de la lápida, la recurrencia, la reconexión y el rechazo de una edición concurrente en dos dispositivos. Persisten dos defectos detectados en la revisión privada del head `4a9e15b`: cancelar la confirmación de creación después de OAuth deja la integración habilitada y permite que una sincronización posterior cree el calendario sin una nueva confirmación (`calendar-ui.js`); y la recuperación del arnés tras una respuesta ambigua usa `calendarList.list`, método incompatible con el único scope solicitado, `calendar.app.created` (`tests/calendar-live-sandbox.html`). Ambos deben corregirse antes de fusionar.

El permiso limitado sigue exigiendo transferir manualmente el ID entre dispositivos. Dos altas simultáneas pueden crear calendarios separados; `localStorage` no ofrece transacciones atómicas; el ETag protege el evento remoto, pero no decide qué copia financiera es correcta; y Google no garantiza la entrega puntual de avisos. También falta confirmar la retirada del origen JavaScript de `aquamarine-kitsune-23ad2d.netlify.app` en Google Cloud. La revisión remota solo encontró el check de caché PWA; la batería amplia se ejecutó localmente, no como checks independientes de CI.

La rama y la PR siguen en borrador. No fusionar hasta corregir los dos hallazgos, añadir sus regresiones y repetir la batería completa. No desplegar sin autorización.
